1majorfix nowlinked ×5Fail-open removes the limit under the conditions it is meant to handle5.8

Strategic robustness · Paragraph 2: "If Redis is unreachable, the gateway fails open and allows the request"

Every request, including ones that will be rejected, costs a Redis call. A big enough flood can therefore degrade Redis, trip fail-open and remove all limits for all tenants at once. An attacker can aim for that state, and any tenant benefits from it. The stated rationale, "we would rather serve traffic than go down", is a false choice: unbounded traffic during a failure can take down the backends the limiter protects. Replace it with a bounded fallback, such as an in-process token bucket on each gateway node set to roughly the tenant limit divided by the node count, with a circuit breaker around Redis. That keeps traffic flowing and keeps a limit in place.

Raised by Nash_Agent, Security Reviewer, The Simplifier, Staff Engineer, Product Lead

2majorfix nowlinked ×4Bucket identity does not match the tenant limit5.35

Incentive compatibility · Paragraph 1: "Each tenant gets a token bucket in Redis, keyed by API key"; Paragraph 2: "configured per tenant"

The limit is stated per tenant but enforced per API key. If a tenant can hold several keys, each extra key adds 100 rps and a 200 burst, so splitting traffic across keys beats the limit at no cost. The subject does not say whether multiple keys are allowed. Key buckets by a canonical tenant ID resolved from the API key, or state and enforce a one-key-per-tenant rule. Account creation also needs a control if separate tenants can be registered freely, because one actor can then multiply the default allowance.

Raised by Nash_Agent, Security Reviewer, The Simplifier, Staff Engineer; backed by Product Lead

3majorfix nowlinked ×4Metrics are an undated promise, leaving fail-open invisible5.2

Commitment credibility · Paragraph 3: "We will add metrics later"

This commitment has no date, owner or release gate, and once the system ships the pressure to deliver it falls. Without metrics the operator cannot detect fail-open, identify abusive tenants, tune limits or show that limits are being enforced. Fail-open is therefore silent, and an attacker can exploit it without being noticed. Make a minimum set a launch gate: fail-open count and duration with an alert, Redis latency and errors, and allowed and rejected counts per tenant. Control the cardinality of the per-tenant metrics.

Raised by Nash_Agent, The Simplifier, Staff Engineer, Product Lead; backed by Security Reviewer

4majorfix nowlinked ×3Handling of invalid or unknown API keys is unspecified4.2

Strategic robustness · Paragraph 1: "keyed by API key" and "The default is 100 requests per second with a burst of 200"

The subject does not say whether keys are authenticated before the limiter runs. 5majorlinked ×2"Unreachable" is undefined, so slow Redis has no specified behaviour4.05

Equilibrium stability · Paragraph 2: "If Redis is unreachable"

The design covers only a clean outage and gives no timeout, retry or circuit-breaker policy. If Redis is slow but connected, gateway requests may stall on the limiter, causing the outage fail-open was meant to avoid. 13minorlinked ×3Whole-second Retry-After penalises compliant clients3.7

Incentive compatibility · Paragraph 3: "Rejected requests get HTTP 429 with a Retry-After header"

At the default 100 rps, a token refills about every 10 ms, but Retry-After is expressed in whole seconds or as an HTTP date. A client honouring a 1-second value waits about 100 times longer than necessary while a client that ignores it can take the tokens as they refill. Rejections carry no penalty, so ignoring the header is the better strategy for a client seeking throughput. Rounding down to 0 would instead invite immediate retries. Add jitter so that clients do not retry together, expose finer-grained rate-limit headers, and apply escalating penalties or a cheap local deny path for clients that keep retrying while limited.

Raised by Nash_Agent, The Simplifier, Staff Engineer

14minorlinked ×3Restart-only limit changes weaken incident response3.5

Commitment credibility · Paragraph 2: "loaded at startup, so changing a limit needs a restart"

Throttling an abusive tenant or granting emergency headroom requires a gateway restart, which is most costly during an incident. That makes the operator's threat to throttle slower and less credible. A rolling restart also leaves nodes running different limits against the same bucket for a period. Signal-triggered or watched-file reload with validation and a last-known-good fallback would remove this cost without harming any legitimate party. If the current model stays, document the rollout procedure.

Raised by Nash_Agent, Security Reviewer, Staff Engineer

15minorlinked ×2Refill time source is unspecified2.9

Strategic robustness · Paragraph 1: "A Lua script refills and decrements atomically"

The subject does not say where the script's timestamp comes from. If gateways pass in their own clocks, skew between nodes can distort refill and create or withhold tokens. As B-4 notes, time that appears to move backwards can produce a negative elapsed value unless it is clamped, and whole-second timestamps would refill in coarse steps at 100 rps. Use Redis server time inside the script with sub-second precision, clamp elapsed time to zero or above, and confirm this is compatible with the Redis version and replication mode in use.

# Rate limiter for the API gateway

Each tenant gets a token bucket in Redis, keyed by API key. A Lua script refills and decrements atomically, so concurrent requests cannot overspend a bucket. The default is 100 requests per second with a burst of 200.

If Redis is unreachable, the gateway fails open and allows the request, because we would rather serve traffic than go down. Limits are configured per tenant in a YAML file loaded at startup, so changing a limit needs a restart.

Rejected requests get HTTP 429 with a Retry-After header. We will add metrics later.
