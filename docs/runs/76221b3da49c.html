Rationale and rubric

Disagreement point: without this design, the owner has a single-reviewer pipeline that (per the planted-bug test) finds the same easy bugs at 1/11 the cost; the Judges have no stake; the only party with a credible threat is the owner (abandon the panel). So the surplus the design must earn is the robustness-to-one-loud-voice gain the offline eval shows (1% vs 19% displacement, at a 3-point value cost). The document is unusually honest — the open incentive questions in Next Steps §6 are exactly the ones I would raise — but honesty about a gap is not a fix. Reading jjv/nash.py and jjv/voter.py confirms four exploits that are each a player's best response, not a hypothetical: (1) a veto-holder labels its own finding's dimension, so tagging any complaint `blocker` in its veto vocabulary forces it into D and the Voter; (2) `change_aversion` is self-reported after seeing the proposal, and with the concave phi a high report both shrinks the Judge's own apparent surplus (earning marginal priority) and taxes everyone else's fixes; (3) the broker counts a sincere `reject` from a non-veto Judge as cheap talk and docks its weight for future runs, so honest reject recommendations are punished — a direct incentive to misreport; (4) two Judges mutually `endorses`/`same_as` each other's findings add 0.5× value per endorsement with no coalition detection, despite the archetype's own principle 10. Equilibrium: the forced-veto settlement is an equilibrium of a ratification step that live runs do not perform (the digest shows a proposal; the binding settlement is solved afterwards), and ties within a severity are broken by finding id, i.e. list order, which the first full review documents as producing the wrong fix list. The objective is sum w·log(1+g), not the Nash product — the +1 destroys the scale-invariance the doc claims, which is why the code comment says "(nearly)". Pareto: the kernel is efficient on its own frontier (checked exhaustively up to EXACT_LIMIT), but value is left on the table: deferred findings are not carried across generate rounds and nothing checks a chosen fix was made, and the default was switched to bargaining on every panel before the live comparison that would justify it. Cheap-talk check on myself: I hold no veto, so my `revise` is advice, not a threat. Who pays for delay: the owner, in API dollars per round; the cheapest next move is steps 1–6 of Next Steps before the web UI, exactly as the doc orders them. Tie-break rule I used for severity: a finding is `major` if a single Judge's unilateral best response changes the Voter's decision or the fix list; `minor` if it only degrades it; `nit` for documentation inconsistency.

# Judge_Jury_Voter

A swarm of AI agents, each embodying the lens of a *best-in-the-business* professional — a staff engineer, a principal product designer, a Stripe-grade technical writer — that collectively **review** and **generate** documentation, code, and designs. Each persona is *inspired by* how such a professional works and what they demand; it is never an impersonation of a specific named person (see "Archetype roster" below). The name encodes the consensus mechanism: independent **Judges** score an artifact, a **Jury** round lets them deliberate and revise, and a **Voter** aggregates the scored verdicts into a single decision plus a prioritized action list. A **Generator** loop wraps the same machinery so the swarm can author from scratch, not only critique.

This document is the design and build plan. It covers the swarm topology, how an archetype is defined, the orchestration rounds, the generation loop, the web interface and API, storage, cost and safety controls, and a phased roadmap.
